BakeOut — App Map

A food-first dating app where Jack & Jill, your cherry wingmen, break the ice and plan a virtual cooking date, then leave the two of you to it.

The main pieces

  • The app (app/, Flutter): one codebase for iPhone, Android, and the web. Screens live in app/lib/screens/, talking to Firebase through small services in app/lib/services/.
  • The server (functions/, Cloud Functions in TypeScript): matching, the wingman's brain (Gemini), date plans, and account deletion. It reacts to documents the app writes.
  • The data (Firestore and Storage): profiles, likes, matches, messages, photos. firestore.rules and storage.rules decide who may read or write what.

One action, end to end: a like becomes a match

You swipe right in Discover. If the other person already liked you (or is a judge-demo profile, which likes back), the server makes the match, the wingman writes the opening message, and both phones play “It's a BakeOut!”.

The route (three stops)

Search for the anchor in your editor (Cmd+Shift+F in Cursor) rather than trusting line numbers; they drift.

1

The swipe writes a like

app/lib/screens/discover/discover_screen.dart, anchor _onSwipe. A right swipe plays the heart burst and calls DiscoverService.like in app/lib/services/discover_service.dart, which writes one document. That's all the app does; it doesn't decide whether it's a match.

The whole “like” on the app side 
Future<void> like(String me, String them) => _db.doc('likes/${me}_$them').set({
  'from': me,
  'to': them,
  'createdAt': FieldValue.serverTimestamp(),
});
2

The server decides it's a match

functions/src/matching.ts, anchors onLikeCreated, handleLike, matchIfMutual. The new like triggers the function. If the reverse like exists and both want the same thing (partner or friends), one match is created inside a transaction, with each person's own cherry. A one-sided like tells the other person who liked them instead. Judge-demo profiles (demoLikesBack) like back straight away.

Proved by functions/test/matching.emulator.test.mjs: “a mutual like creates exactly one match, each person with their own cherry”.

3

The wingman opens the chat, and the app celebrates

functions/src/cherry/opening.ts, anchor openChat: the new match triggers cherryOpening, which finds real common ground and asks Gemini for a friendly opener. Back in the app, app/lib/screens/home_shell.dart, anchor _celebrate, is listening for unseen matches and shows “It's a BakeOut!”, then “Let's Break the Ice!” opens the chat.

A practice to reuse

Write the observable result first, then make a test check exactly that. The build checklist's slice 6 said, before any code: “a one-sided like creates no match; a mutual like creates exactly one match with both cherry assignments.” Those sentences became the tests in functions/test/matching.emulator.test.mjs. When the judge demo later needed profiles that like back, the change was one more sentence (“a demo profile likes back, so the like becomes a match with no ‘liked you’ notice”), one more test, and a few lines in handleLike. All seven matching tests then showed the old behaviour still held.

On another project: before asking an agent to build something, write one or two sentences someone could check by watching it happen, and ask for a test that checks exactly those sentences. A change later is then “add a sentence, add a test”, not “hope nothing broke”.
