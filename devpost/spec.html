How BakeOut is built: a Flutter app on iPhones, Firebase for accounts, data, live chat and photos, and Cherry's brain running on Firebase's servers with Gemini.

How this works, in plain language

📱 The app (Flutter)Every screen, plus the selfie check, which runs entirely on the phone.
🔥 FirebaseLogin (Auth), a live shared database (Firestore), and photo files (Storage).
🍒 Cherry's brainCloud Functions that wake up on each message or every minute, ask Gemini what to do, and write Cherry's reply.

Vinamra types "I'm terrible at pasta 😅" → it's saved to Firestore → the other phone shows it instantly → a Cloud Function sends the recent chat and both profiles to Gemini → Gemini says stay quiet, they're chatting happily. Two quiet minutes later, the timer notices the stall and Cherry asks about their shared love of Italian food.

Only one Cherry per chat, the Gemini key never inside the app, and selfies never leave the phone.

Details

🔍 The useful unknown: on-device face verification

In scope you expected it "should not be very hard." It's really two jobs: the live check (a face detector handles this well) and matching the selfie to the profile photo, which needs a face model that no single Flutter library packages up.

First build step: a small trial on your own photos. Evidence needed:
  1. The face detector picks up a blink and a head turn on an iPhone.
  2. The .tflite model loads and runs on iOS.
  3. Same-person pairs score clearly above different-person pairs, so a threshold can be picked.
If (3) fails, that's a plan revision you decide on.
🗂 Data model (Firestore)
  • users/{uid}: public profile: name, age, gender, interestedIn, city, lookingFor, photos, verified, cherryAvatar, food{…}, prompts
  • users/{uid}/private/account: date of birth, email (owner only)
  • users/{uid}/passes, /recipes: hidden people; cached recipes
  • likes/{from}_{to}
  • matches/{a}_{b}: users, cherryFor, cherryState, timing fields, datePlan{status, dish, day, time, confirmedBy}
  • matches/{id}/messages: text · dateCard · recipe · song · cherryGoodbye
  • Never stored: verification selfies
🛡 Cherry's guards (in code, not just the prompt)
  • Every function stops if cherryState == "left".
  • Never posts twice in a row.
  • After a declined date, no new proposal until both have chatted more.
  • cherryBusyUntil lock so two triggers can't both speak.
  • Any card change clears both confirmations; "confirmed" only when both tap Confirm.
⚠️ Failure modes
  • Gemini slow or invalid: Cherry stays quiet and retries next time; never posts a half plan.
  • Face match fails for a real person: retry with tips; one tunable threshold.
  • Both phones trigger Cherry: the lock lets only one speak.
  • Discover empty: the Recipes page.
  • Recipe ignores an allergy: restrictions sent every time, plus an allergy note; reduced, not eliminated.
✂️ What was simplified
  • Phone reports its own verification result (a tampered app could fake it).
  • Discover filters in the app, no algorithm.
  • One-minute timer for stalls and reminders.
  • Public age, private date of birth.
  • No push notifications; iPhone only.
▶️ How to run it
  • Once: Firebase project on Blaze with a budget alert · enable Email/Password, Firestore, Storage · firebase functions:secrets:set GEMINI_API_KEY · flutterfire configure · firebase deploy --only functions,firestore,storage
  • Each of you: cd app && flutter pub get && flutter run -d <iPhone>
  • Demo: make both accounts beforehand; reinstall within 7 days of recording.
